# etlui

## Purpose

Vue 3 + TypeScript front-end (Vite 7, Pinia 3, vue-router 4, axios, Tailwind 4, shadcn-vue on `reka-ui`, `@lucide/vue`, `vue3-hot-toast`) that drives the PRIDE-C pipeline. It calls the REST API of `etlhub` (port 8111) and follows jobs over its log WebSocket. It has no backend of its own: in production it is static files served by nginx.

## Rules

- **The `etlhub` contracts are frozen** (copied from `etlhub/CLAUDE.MD`): `ETLResponse` = `{status, message, job_id, webhook_url}`. `JobStatus` = `{status, job_id, started, completed, logs, message}`. `job_id` = `<task_type>_<uuid4 hex[:8]>`. WebSocket messages: `etl_log_history`, `job_status_update`, `etl_log_entry`, `etl_log_complete`, close codes `4004` (unknown job) and `4401` (no session: `useWebSocketLogger` clears the store and goes to `/login`). Any change must be mirrored in `etlui/src/composables/useWebSocketLogger.ts` and `usePipeline.ts` / `services/pipeline.ts` in the same change, and on the `etlhub` side too. Never change a contract on one side only.
- **Never trigger real jobs against a real DHIS2 or the host** from the dev UI without explicit approval. The dashboard buttons call `/import_*`, `/build_analytics`, `/post_forecast`, `/update_key` (write to DHIS2), `/forecast/` (`docker run`) and `POST` / `DELETE /input/files/{name}` (overwrite or delete files in `input/`). Use an `etlhub` running with `DRYRUN=true`. Tests mock `@/services/api` (or the service module), never a real backend.
- **Layering**: `views` → `composables` / `stores` → `services` → `types`. `router` only reads `stores/auth`. HTTP calls (`axios`, `fetch`) live in `services/` only. The WebSocket lives in `useWebSocketLogger.ts` only. Views do not import `@/services/*`; they go through a composable or a store. Existing violations are known debt (see Gotchas): do not add new ones, do not refactor them unless asked.
- **Composables orchestrate, they hold no business rules.** The pipeline rules (order, run context, cycle, confirmations) live in etlhub (`etlhub/docs/decision-design/pipeline-checkpoints/pipeline-checkpoints.md`); etlui only shows `GET /pipeline/checkpoints` and never computes a ✓. A composable calls a service, updates state, notifies. Follow `usePipeline.ts` / `useInputPreview.ts` (service calls only, typed).
- **No long blocking `await`.** A launch endpoint returns 202 with a `job_id`. Never wait for a job to finish inside a click handler: follow it through the WebSocket or a polling loop that stops on `success` / `error`.
- **Never print or copy secrets.** Do not log the token, `DHIS_TOKEN` or the `Authorization` header. Mention variable names only (`VITE_API_BASE_URL`, `VITE_DHIS2_URL`).
- **Never hardcode a DHIS2 URL or the API URL.** Use `import.meta.env.VITE_*`. The only allowed literal is the existing `http://localhost:8111` fallback; do not add new copies of it (there are two: `services/api.ts` and `App.vue`, for the header's API Docs link; elsewhere use the axios `baseURL`).

## Gotchas

- **Pipeline (since 2026-10-09)**: every launch can answer 409 `{message}` (order, lock, no open run) or 409 `{code: 'confirmation_required', message, impact}`; `usePipeline` shows the first and opens `ImpactDialog` for the second. `DISEASE_CODE` / `OU_LEVEL` come from the open run (server side): etlui sends none. Opening a run (`POST /pipeline/runs`) **empties `input/` and `output/`** on the server. The test mode button calls `PUT /pipeline/mode` (`{test_mode}`, etlhub's `TEST_MODE`); leaving it pauses the active test pass (since 2026-10-22, nothing is discarded). It does not switch DHIS2 writes: `DRYRUN` comes from `.env`, copied into Redis at each etlhub start, not editable from etlui yet (`etlhub/docs/decision-design/dry-run-merge/`), shown read only (`dry_run` in `GET /pipeline/checkpoints`). The `<input type="month">` of Home (since 2026-10-26; the Dashboard only shows the cycle) calls `PUT /pipeline/cycle` (`usePipeline().setCycle`): the month the next launch starts a pass on; disabled while a pass is active. **Passes (since 2026-10-22)**: `state.pass` is the pass shown; "Pause the cycle" and "Abandon the cycle" (confirm dialog) sit after System Update while it is active (`usePipeline().pause`, `abandonPass`); a paused pass is resumed from Home or the Journal. See `etlhub/docs/decision-design/cycle-passes/cycle-passes.md`.
- **Pipeline revision (2026-10-12)**: step 1 has the `approve_imports` decision (`POST /pipeline/imports/approve`, not a card; since 2026-10-26 its Approve imports / Reject buttons are in the `footer` slot of `ImportAvailabilityDialog`, opened by Details: a click closes the dialog, then decides); `external_data/<fkt|csb>` is a mandatory item shown with its status (the run no longer has an `external_data` field); the run shows the expected config file per disease (`CONFIG_FILES` in `src/config/pipeline.ts`); step 3 is `build_analytics` → `update_key`. Still pending in etlhub: `calc_orgunit_alerts` (501) and the test-mode scope (`etlhub/docs/decision-design/pipeline-checkpoints/pipeline-checkpoints.md` §8).
- **WebSocket `4004`** (since 2026-10-08) means **unknown job** only. A pending or running job without logs yet gets an empty `etl_log_history` and stays open, so `useWebSocketLogger` follows it from the 202 on. Forecast logs still arrive only at the end: during a forecast you see status updates, not log lines. `useWebSocketLogger` defaults its base URL to the axios `baseURL` and maps `https` to `wss`. The tracking page uses it in the request detail modal for pending/running jobs.
- Login: the DHIS2 token stays in etlhub; the browser only holds the `etlhub_session` cookie (HttpOnly, SameSite=Strict, Secure). Every request to etlhub must send credentials (`withCredentials` / `credentials: 'include'`), and POST/PUT/DELETE must come from `FRONTEND_URL` (etlhub checks `Origin`). `ConfigView.vue` shows the DHIS2 URL and token status read-only. Every etlhub route except login/logout needs the session, the log WebSocket included.
- `services/api.ts` defaults `baseURL` to the absolute `http://localhost:8111`, so the Vite proxy (`/api`, `/auth` → `:8111`) is bypassed in dev and `etlhub` must allow CORS (it does, `api/middleware.py`). Most endpoints (`/import_*`, `/fetch_*`, `/forecast`, `/output`, `/input`) are not in the proxy anyway.
- `vite.config.ts` sets `envDir: '../../'`, i.e. the **parent of the repo**, not the repo root. The root `.env` defines `VITE_*` variables, but Vite does not read them from there (read from the config, not executed).
- Ports: Vite dev uses its default (5173, no `port` set). nginx listens on **8000**, but the `Dockerfile` says `EXPOSE 8111` (the API port). The `etlui` service is commented out in `compose.yaml`.
- A 401 from any axios call clears the store and does a hard `window.location.href = '/login'`.
- Navigation: the hamburger button of the `App.vue` header opens `Drawer` (right side, `navItems` + API Docs). `/` is `HomeView` (route name `Home`, start or resume a pass); the dashboard (`Dashboard.vue`, route name `Dashboard`, where login lands) is at `/forecast`.
- Toasts: `useNotification().showNotification` calls `vue3-hot-toast` directly, bottom-right. Its hover pause is broken in 0.0.5 (dismiss timers never cleared): every toast has an infinite duration and `useNotification` closes it (`closeAfter`), never while the pointer is on the toasts (`[data-toasts]:hover`, checked again every second), so within 1 s after it leaves. The `<Toaster />` sits in a `popover="manual"` div (`App.vue`, `data-toasts`) shown on mount: it is in the top layer, above every dialog (they are portals with a z-index). The toasts stay usable over an open modal (hover pause, clicks; their own `pointer-events: auto` beats the `pointer-events: none` Reka puts on `body`), and `components/ui/dialog/DialogContent.vue` keeps the dialog open when a toast is clicked (since 2026-10-27, checked by its spec). Probably (read from Reka's `hideOthers`, not checked) the toasts are `aria-hidden` while a modal is open, so screen readers would not announce them then.
- There is no TS type for `ETLResponse` or `JobStatus`: responses are read untyped (`response.data?.job_id`).
- Views importing services (layering debt): `api` called directly in `Dashboard/components/ForecastReportModal.vue`; `@/services/auth` in `Auth/LoginForm.vue` (`login`) and `Auth/ParametersPage.vue` (`logout`); `RequestLog` type imported from `@/services/api` in `TrackerView/` and, type only, in `types/pipeline.ts` (`JournalEvent.request`).
- `useActivityLog()` creates a new list on every call: `usePipeline` takes the page's `addActivity` as a parameter.
- The `api` instance defaults to `Content-Type: application/json`, which makes axios serialize a `FormData` as JSON. Pass `multipart/form-data` explicitly for uploads (see `services/inputs.ts`).

## Commands

Run from `etlui/`. Yarn 1 is the package manager (`yarn.lock`; the `Dockerfile` runs `yarn install --frozen-lockfile`). There is no `package-lock.json`: do not create one.

- Install: `yarn install`
- Dev: `yarn dev` (Vite; needs `etlhub` on `:8111`, proxy `/api` and `/auth`)
- Build: `yarn build` (output `dist/`, git-ignored). `vite build` does **not** type-check.
- Preview: `yarn preview`
- Tests: `yarn vitest run` (there is no `test` script). 23 files, 119 tests, all passing. Specs: `teleport` is stubbed in `src/test/setup.ts` so dialog content stays in the mounted wrapper; a dialog's content appears a tick after it opens (`await flushPromises()`), and a closed dialog renders nothing.
- One file: `yarn vitest run src/composables/__tests__/usePipeline.spec.ts`
- Type-check, linter, formatter, coverage: none installed (`vue-tsc`, ESLint, Prettier and `@vitest/coverage-*` are absent). Do not invent one.
- Docker: `docker build -t etlui etlui/` → nginx on 8000.
- Node 22 (`.nvmrc`, same as the `Dockerfile`): `nvm use` first. Add a shadcn-vue component: `npx shadcn-vue@2.8.2 add <name>` (the CLI needs Node ≥ 22). Add only what a lot uses; review the diff of `base.css` after each `add`.

## Method for new code (adapted from `etlhub/CLAUDE.MD`, proposed)

- Work with the **ponytail** skill (root `CLAUDE.md`): native HTML/CSS before a component or a dependency, then the shadcn-vue component (`src/components/ui/`, added with its CLI), reuse `src/config`, services and composables before adding one; mark deliberate shortcuts with `ponytail:`. Dependencies: yarn only.
- Behaviour and its test ship in the same commit. For a new composable, store action, service call or bug fix, write the failing test first. If you did not, say what you did instead of claiming TDD.
- Specs select with `[data-test="…"]`, a role / tag or an ARIA attribute, never a styling class or `classes()` (since 2026-10-27: shadcn components replace those classes).
- Test behaviour, not implementation: state after a call, the request sent (endpoint, params vs body, headers), what the user sees. Mock `@/services/api` (or `WebSocket`), never the backend. Templates: `services/__tests__/inputs.spec.ts` (request sent), `composables/__tests__/usePipeline.spec.ts` (service mocked, state + notification + confirmation), `views/Dashboard/__tests__/Dashboard.spec.ts` (what the user sees), `utils/__tests__/preview.spec.ts` (pure functions).
- `router/__tests__/guard.spec.ts` redefines the guard inside the test instead of importing `@/router`: it does not test the real guard. Do not copy that pattern.
- New or changed functions and composables: at most 50 lines and 4 parameters, typed (no new `any`), no empty `catch {}`, no `console.log` (the TS equivalents of `except … pass` and `print(`).
- Coverage: no baseline can be measured (no coverage tool installed). Add tests for what you touch.

## Required checks

- Run `yarn vitest run` before and after any change, and `yarn build` after it.
- Changed a call to an `etlhub` endpoint or a contract field: check the frozen contracts above and `etlhub`'s endpoint table; update `useWebSocketLogger.ts`, `services/pipeline.ts` / `usePipeline.ts`, `etlhub`, and the docs in the same change.
- Sending parameters to an endpoint: check in `etlhub` whether it reads query params or a body, and that the parameter exists.
- No new HTTP call outside `services/`, no new `services` import in a view.
- No secret, token or DHIS2 URL in code, logs or tests.
