# etlhub

## Purpose

FastAPI service (port 8111) that exposes the PRIDE-C ETL scripts (`etl/scripts/*.py`) and the R forecast pipeline over HTTP. Long jobs run in Celery workers, state lives in Redis, logs are streamed over WebSocket. Consumed by the Vue front-end `etlui`.

## Module map

- `core/` — config, `dependencies.py` (composition root), `celery_app.py`, `job_context.py` (mode served, a job's pass config, `work_dir`), `request_context.py` (a request's actor and `request_id`)
- `domain/` — exceptions (`AuthStoreUnavailable`, `DHIS2Error` among them), `pipeline.py`, 15 ports (`interfaces/`: `JobRepository`, `TaskLauncher`, `PipelineGate`, `RequestTrackerProtocol`, `DefaultFileSource`, `EventPublisher`, `EventSubscriber`, `AuthStore`, `ConfigRepository`, `FetchedImports`, `DHIS2Reader`, `DHIS2Accounts`, `WebhookNotifier`, `OutputFiles`, `ImportSettings`), Pydantic DTOs (`schemas/`)
- `application/use_cases/` — `*_service.py` (generate `job_id`, launch through the `TaskLauncher` port), `etl_use_cases.py` (`ETL_JOBS`, stdout capture, `notify_webhook` through `WebhookNotifier`), `validation_use_cases.py`, `check_import_availability.py` (`GET /import_availability`, DHIS2 read through `DHIS2Reader`, its configuration through `ImportSettings`), and etlhub's own job functions: `build_analytics.py`, `calc_alerts.py`, `fetch_pivot.py`, `gee_import.py`, `post_forecast.py`
- `infrastructure/` — `tasks.py` (`task_etl`, `task_forecast`, `CeleryTaskLauncher`), `job_store.py`, `request_tracker.py`, `config_store.py`, `auth_store.py`, `forecast_runner.py`, `etl_events.py` (live job events, Redis pub/sub: `publish_*` and `RedisEventSubscriber`), `checkpoint_store.py` (pipeline gate, passes, journal), `fetched_imports.py`, `default_files.py`, `redis_client.py`, `dhis2_reader.py` (`HttpDHIS2Reader`), `dhis2_accounts.py` (`HttpDHIS2Accounts`: login's `/api/me` and PATs), `webhook_notifier.py` (`HttpWebhookNotifier`), `output_files.py`, `import_settings.py` (`WorkDirOutputFiles`: report and `output/` archive)
- `api/` — `routers/`, `websockets/etl_logs.py`, `auth/` (DHIS2), `middleware.py`
- `tests/` — `api/`, `infrastructure/`, and at its root `test_architecture.py` and the use-case tests

Siblings in the repo:
- `etl/scripts/` is **imported in-process** by etlhub, `etl/scripts/config.py` is the CLI version (env / `.env` only) and must never import `etlhub`; `etlhub/script_config.py` (imported by `etlhub/__init__.py`) replaces its `_get` / `_dhis2_credential` with Redis and the login.
- `forecast/` (R) runs through `docker run` from the worker. Files are exchanged through `input/` (ro) and `output/` (rw).
- `etlui/` consumes the REST API and the WebSocket (see contracts below).

## Rules

- **Never call real endpoints against a real DHIS2 or the host.** `/import_gee`, `/build_analytics`, `/post_forecast`, `/update_key` and `POST /pipeline/imports/approve` (approve) write to DHIS2 (`/import_pivot_*` only fetch from Pivot since 2026-11-20, kept in Redis per pass and mode since 2026-11-23 (`infrastructure/fetched_imports.py`); the approval posts the elements chosen: `docs/decision-design/pivot-approval/pivot-approval.md`). `/forecast/` runs `docker run`. `POST /pipeline/runs` empties `input/` and `output/`. They only need a session, which a logged-in user has. Manual runs: in test mode only (DRYRUN = TEST MODE: production writes). Tests use `app.dependency_overrides`, never a real Celery or Redis.
- **Never print or copy secrets.** `.env`, `.env.debug` and `.gee-private-key.json` exist locally. Mention variable names only.
- **The `etlui` contracts are frozen.** `ETLResponse` = `{status, message, job_id, webhook_url}`. `JobStatus` = `{status, job_id, started, completed, logs, message}`. `job_id` = `<task_type>_<uuid4 hex[:8]>`. WebSocket messages: `etl_log_history`, `job_status_update`, `etl_log_entry`, `etl_log_complete`, close code `4004`. Any change must be mirrored in `etlui/src/composables/useWebSocketLogger.ts` and `etlui/src/services/pipeline.ts` in the same change.
- **Respect the architecture below** (hexagonal). Do not mix the layers, even to shorten a diff: ponytail never removes a port or a layer.
- **Adding a Celery job type = 3 changes**: script function in `ETL_JOBS` (`etl_use_cases.py`; `task_etl`, `CeleryTaskLauncher` and `IngestionService.launch` then accept it), the job in `domain/pipeline.py`, one entry in the `api/routers/etl/ingest_router.py` table (or `add_launch_route`), which returns 202 with `ETLResponse`. Shared `confirm` query params live in `api/routers/__init__.py`.
- **HTTP handlers are plain `def`** (FastAPI threadpool, since 2026-11-27): every launch runs `CheckpointStore.start` (SQLite, Redis, files). `tests/api/test_handlers_off_the_event_loop.py` fails on any `async def` HTTP route but `GET /`. The log WebSocket stays `async` and runs its blocking calls through `asyncio.to_thread`. Long work still goes to Celery.
- **Do not move or rename `etl/scripts` modules**, and do not touch the `os.chdir` (`main.py` and `migrate.py`) or the `sys.path` changes (`main.py`; the worker gets the repo root through `python -m`). Worker and API depend on them, and scripts write under `os.getcwd()/input|output`.

## Architecture (hexagonal, to respect)

Imports go inward only:

| Layer | May import (etlhub) | Holds |
|---|---|---|
| `domain/` | nothing | rules (`pipeline.py`), DTOs, exceptions, **ports** (`interfaces/`, `typing.Protocol`) |
| `application/` | `domain`, `core.config`, `core.job_context`, `core.request_context` | use cases; they talk to the outside **only through ports** |
| `infrastructure/` | `domain`, `application`, `core` but `core.dependencies` | adapters (Redis, SQLite, Celery, Docker, HTTP) implementing the ports |
| `api/` | `application`, `domain` DTOs, `core` | HTTP / WebSocket; gets services and adapters by injection |
| `core/` (other modules) | `core` | settings, Celery app, contextvars |
| `script_config.py`, `migrate.py` | `infrastructure` (and `core.config`, `core.job_context`, `core.request_context`) | adapter of `etl/scripts/config.py`; migration CLI |
| `core/dependencies.py`, `main.py`, `run_*.py` | everything | composition roots: `core/dependencies.py` binds every port `api` and `application` get (A4 below for the others) |

- A use case annotates its collaborators with **ports**, never with an `infrastructure` class, not even under `TYPE_CHECKING`.
- `api` gets services and ports from the getters of `core/dependencies.py` (`Depends(get_…)` in a route signature; a direct call such as `get_auth_store()` in middleware, helpers and `get_current_user`); it never imports `etlhub.infrastructure`. An adapter may be a module whose functions implement the port (`auth_store`, `etl_events`).
- A new adapter method used by a use case or a router goes into its port in the same change. A new adapter gets a port when `application/` uses it.
- A port with a single adapter is normal (the second implementation is the test fake): never delete a port as dead code or "yagni".
- Third-party libraries per layer (since 2026-11-27, owner's decision): `domain` stdlib + `pydantic`; `api` stdlib + `fastapi`, `starlette`, `pydantic` (no `redis`, `httpx`: an adapter's error reaches `api` as a domain exception, `AuthStoreUnavailable`, `DHIS2Error`); `application` stdlib + `pydantic`, plus, per file, the libraries of the ETL copies (`etl`, `httpx` in `build_analytics.py`, `pivot_dhis_tools`, `pridec_gee`, `ee`, `pandas`, `geopandas`: the list is `THIRD_PARTY_FILES` in the test); `core` `pydantic_settings` (`config.py`), `celery` (`celery_app.py`), `fastapi` (`dependencies.py`); I/O libraries (`redis`, `httpx`, `requests`, `docker`...) otherwise only in `infrastructure`, which may import any.
- `tests/test_architecture.py` walks every source file outside `tests/` (layers, `core/`, root files; a file with no rule fails) and every import (lazy, `TYPE_CHECKING`, relative ones resolved, `from etlhub import x`), against both rules above. Its `ALLOWED_DEBT` is empty since 2026-10-23: never add an entry, fix the code. It sees imports only: a call through an object it cannot see (e.g. a client passed in) is not checked.
- Tolerated, pending the team's decision: `application` → `etl.scripts` and the libraries they need (the ETL copies, per file in the test; `validation_use_cases.py` reads the files with pandas/geopandas), `api` → `domain` DTOs. `ingestion_service.py` reads `pridec_gee.AVAILABLE_VARIABLES` (a constant list, not an ETL copy): accepted by the owner (2026-11-27), named in the test. Nothing else outside the ETL copies imports an ETL library: `check_import_availability.py` reads its configuration through `ImportSettings` and computes its periods itself (`_last_months`, checked against `create_period_range` by `tests/test_library_constants_sync.py`).
- A1, the pass rules live in the store: `infrastructure/checkpoint_store.py` (`PipelineGate`) holds the pass state machine and raises the domain exceptions, so that check and write share one SQLite transaction (a refused launch writes nothing). `domain/pipeline.py` keeps the pure rules; testing the pass rules needs SQLite (`checkpoint_store` fixture).
- A3, context: the mode served and a job's pass config (`core/job_context.py`) and a request's actor and `request_id` (`core/request_context.py`) are `contextvars` every layer but `domain` may read, without a port.
- A4, adapters built outside `core/dependencies.py`: the worker side in `infrastructure/tasks.py` (`JobStore()`, `get_checkpoint_store()`, `etl_events`, `RedisFetchedImports()`, `HttpWebhookNotifier()`), the `main.py` lifespan (`ConfigStore().load_env()`, `check_schema()`), `script_config.py` (Redis config, `pass_config()`, `auth_store.get_credential`) and `checkpoint_store.py` (`ConfigStore()`). Otherwise `core/dependencies.py` is the only binding: `api` gets every port there, and `application` receives them from it or from the worker side above.
- No type checker runs: nothing checks that an adapter or a test fake matches its port. Keep them in sync by hand.

## Gotchas

- **Cycle journal (since 2026-10-19)**: every write of `CheckpointStore` appends to `pipeline_events` through `_event`, in the same transaction, except `set_cycle` (a choice, not pass work) and the first transaction of `change_input` (lock and `running`; the upload or delete is journaled when it ends). A new write method must call it too (one test per write method). The actor and `request_id` come from `core/request_context.py` (a per-request dict set by `RequestTrackingMiddleware`, `actor` set by `get_current_user`); outside a request (Celery worker) the actor is `worker`. Test-mode events live in the Redis blob only, kept when test mode is left. `request_log` lines flagged `journal` are never purged.
- **Cycle passes (since 2026-10-22)**: a pass is one run of a cycle (month); `checkpoints`, `forecast_runs` and `pipeline_events` carry its `pass_id` (table `passes`: active, paused, complete, abandoned; one active per mode). Every write goes to the active pass (`_current`); a launch starts one on the target month, after a complete pass only with `confirm=true`; on a month whose last pass is paused, a launch gets 409 `confirmation_required`, and with `confirm=true` starts a new pass (the paused one stays paused, to resume with `POST /pipeline/passes/{id}/resume`). A pass stays active until the user pauses, abandons or completes it: a calendar month change no longer pauses it (since 2026-11-20; leaving test mode did until 2026-11-19: the mode is now per user). A launch that starts a pass **carries over** the imports (and `approve_imports`) done in another pass of the cycle with the same `params` and `dry_run`, both kept in every import's `launched` event since 2026-10-26 (`carried_over` events; `cycle-passes.md` § 11). Migration 1 (`_migrate_to_passes`) converts a month-keyed store (cut after each `cycle_closed`). See `docs/decision-design/cycle-passes/cycle-passes.md`.
- **Schema migrations are run by hand only (since 2026-11-04)**: `python -m etlhub.migrate` (`--check` lists what is pending), API and workers stopped; it backs each db up next to `etlhub.db` first. `PRAGMA user_version` must equal `SCHEMA_VERSION` (`len(CheckpointStore.MIGRATIONS)`), for `etlhub.db` and the test blob: a db behind or ahead makes the API refuse to start and every pipeline call raise `SchemaVersionError`. A change to `_SCHEMA` ships with a new migration at the end of `MIGRATIONS` and its test on a db of the previous version; never edit a released one. No down-migrations: going back = restore the backup. See `docs/decision-design/db-migrations/db-migrations.md`.
- **Foreign keys (since 2026-11-18, schema version 2)**: `pass_id REFERENCES passes(id)` on `checkpoints`, `forecast_runs`, `pipeline_events`, `availability_checks`, enforced by `PRAGMA foreign_keys = ON` in both store transactions: insert the pass before its rows, never delete a referenced pass. `request_id`, `cycle` and `job_id` stay plain columns (why: `docs/decision-design/foreign-keys/foreign-keys.md`).
- A Celery task must **re-raise** after writing the "error" status, or Celery reports success.
- `_update_task_status` merges with the existing record. Do not overwrite `started` or `logs`.
- **Every job is a Celery job (202)**: `/post_forecast` since 2026-11-24, `/update_key` and `POST /pipeline/imports/approve` (approve; reject stays 200) since 2026-11-27. Nothing runs inline in the API process: no job redirects the API's `stdout`. A job function may return a string, its end message (post_forecast: a CSB run's alerts not included; approve_imports: the elements posted, each element's outcome in `GET /pipeline/imports/fetched`). During a job the root logging handler writes into the job's `_JobLogger` (each script's `setup_logging()` runs `basicConfig(force=True)` under the redirect): code called from `_JobLogger.write` (`JobStore.append_logs`) must log through its own non-propagating logger, or a failure loops until `RecursionError`. `_execute_etl_job` restores the root handlers and level after each job.
- `GET /import_availability` (since 2026-10-26) is **synchronous but off the event loop** (a sync `def`, FastAPI threadpool): it runs `availability_report()` of `application/use_cases/check_import_availability.py`, read only, with the session's DHIS2 token, and journals `availability_checked` (or `availability_reused`) in the shown pass (so it is tracked too). Each section (one import) is stored in `availability_checks` and reused by every user of the cycle until that import is launched again, a `build_analytics` succeeds (since 2026-11-23), its parameters change or 30 days pass (`?refresh=true` skips the reuse). Its periods, CSB ids and codes are copied from the three import scripts: keep them in sync. See `docs/decision-design/import-availability/import-availability.md`.
- **Configuration fixed by a pass (since 2026-11-20; schema version 4 since 2026-11-27)**: when a pass starts (`POST /pipeline/passes`, or a launch with no pass active) it fixes `PASS_CONFIG` in `passes`: `gee_variables` (the choice over `pridec_gee.AVAILABLE_VARIABLES`; NULL = all), `dry_run` (the mode's, recorded only: see DRYRUN = TEST MODE below), `parent_ou`, `log_level`, `pivot_url` (since 2026-11-27) (Redis then) and `dhis_url` (the last login), journaled with `pass_started`. Nothing changes them after, except `gee_variables`: each accepted `import_gee` launch with `gee_variables` in its body rewrites it (etlui's Import GEE dialog always sends them; no body keeps it, a refused launch changes nothing; `gee-import.md`). A launch from a session on another DHIS2 is refused (409, `_check_config`); a Celery job gets its pass's config with its launch (`job_context.job_pass_config`), read by `script_config._get` for `PASS_KEYS` (outside a Celery job: the active pass's, `pass_config()`); `_dhis2_credential` refuses a credential of another DHIS2. `GEE_VARIABLES` is no editable key; `GET /api/config` lists the variables read only. Passes from before have NULLs and behave as before. See `docs/decision-design/pass-config/pass-config.md`.
- Editable config (`app:config:dynamic`, `config_store.EDITABLE_KEYS`: `PARENT_OU`, `OU_LEVEL`, `DISEASE_CODE`, `LOG_LEVEL`, `PIVOT_URL` (since 2026-11-20, read by `fetch_pivot.pivot_url()`; `PIVOT_TOKEN` stays in the environment, never in Redis: `GET /api/config` returns `has_pivot_token` only)) is copied from etlhub's `.env` (`ENV_FILE`) at each API start (`PARENT_OU`, `LOG_LEVEL` and `PIVOT_URL` then apply to the passes started after: a pass fixes its own; shared by both modes, by decision: `mode-isolation.md` §6) (`main.py` lifespan, overwriting; a key missing from `.env` is removed; the API refuses to start if Redis fails) and by `PUT /api/config/reload`; `PUT /api/config` edits them all (`DRYRUN` is no editable key since 2026-11-23: the mode decides it). Under etlhub the ETL scripts read these keys from Redis only (`etlhub/script_config.py`; absent = default, Redis error = job fails); the forecast container does not get them (no env since 2026-11-25). The CLI never reads Redis.
- **DRYRUN = TEST MODE (owner's rule of 2026-11-20, applied since 2026-11-23):** test mode ⇒ every job is a dry run, production ⇒ every job writes to DHIS2. Nothing else chooses it: no `dry_run` launch parameter or `POST /pipeline/passes` body field (a client sending one is ignored), no Home switch, no `DRYRUN` of `.env` (the CLI's only). It is the mode served: `CheckpointStore.default_dry_run()` journals it with each launch (`launched` `dry_run`), and the scripts read it through `script_config._get("DRYRUN")` = `current_test_mode()` (a Celery job runs in its launcher's mode; never `.env`). Nothing carries a `dry_run` to the job. Passes from before follow it too: the `dry_run` a pass stored is ignored, the API shows the mode's (`_passes`). `update_key` in test mode is refused (409: `pivot_dhis_tools` ignores its `dryRun`). Production now writes: never launch a production job against a real DHIS2 without approval.
- `JobStore` and `RequestTracker.save` log their failures at `WARNING` and go on (a storage failure never fails a job). `_JobLogger.write` still ignores a failed live-event publish (the line is already in the history). A job missing from Redis does not mean it failed: `logs/{id}.log` keeps its logs.
- On a job failure, `_run_task` appends the traceback to the job log (file and Redis).
- The WebSocket closes with `4004` only for an unknown job; jobs are `pending` from the 202 on, so the socket stays open for them. Job logs (ETL and forecast) are appended as they are printed (`JobStore.append_logs`, Redis and `logs/{id}.log`), so the socket streams them live.
- Forecast: `HOST_PWD` is read from `Settings.host_pwd`: the worker's environment, else etlhub's env file (`ENV_FILE`, root `.env` by default); it must be a **host** path. Forecast paths must be under `input/` (422 otherwise). The forecast runs on the Celery queue `forecast`: its worker needs the Docker socket (`run_celery` without `-Q` serves both queues). There is no timeout, by decision. The container is sandboxed: `--network none`, no env but `HOME=/tmp` (with `--user`, when the worker is not root), `--cap-drop ALL --cap-add SYS_NICE`, `no-new-privileges`, image `FORECAST_IMAGE` = tag `1.1.0` (same as `compose.yaml`) plus its digest.
- One job at a time, in cycle order: every launch, upload and input delete goes through the pipeline gate (`CheckpointStore`, SQLite `logs/etlhub.db`) and gets **409** otherwise. Three steps (`data_import`, `forecast`, `system_update`); the forecast step is 9 runs (source × disease), one open at a time (`POST /pipeline/runs`), and run jobs need it (409 otherwise). **Opening a run empties `input/` and `output/`** and writes `DISEASE_CODE` / `OU_LEVEL` into the dynamic config at each run job. A new job type must be added to `domain/pipeline.py` (`PIPELINE`, and `RUN_TASKS` if it belongs to a run), or `resolve_slot` raises. A step counts only if the previous one does (`progress()` is chained), and undoing a `success` needs `?confirm=true` (409 `confirmation_required` with `impact` otherwise); launch routes pass `confirm` down to the gate. API messages are in English. The cycle follows the calendar month unless chosen with `PUT /pipeline/cycle`; a month change leaves the active pass active on its month (since 2026-11-20). Test mode (since 2026-11-19 **per user**: `PUT /pipeline/mode` writes the caller's session, a session starts in test; the global `pipeline:test_mode` key is gone): passes live in Redis only (in-memory SQLite serialized in `pipeline:dry_run:db`), files in `test/input` and `test/output`; each mode keeps its own active pass, but a user leaving a mode whose pass is active must pause or abandon it (`leave_mode`: 409 `confirmation_required` with `impact.actions`, then body `pass_action`; journaled `cause: mode_change` with its reason). **One job lock for both modes**: the `pipeline_lock` row of `logs/etlhub.db`, attached as `shared` to every test-mode transaction (`BEGIN IMMEDIATE`, Redis lock first, never the other way); a job of the other mode shows as `job_id` null, task `a job of the other mode`. `POST /calc_orgunit_alerts` (CSB runs) is a Celery job since 2026-11-24 (`calc_alerts.py`: writes `output/alerts.json`, posted by `post_forecast`). A killed worker keeps the lock until `DELETE /pipeline/lock` (it never expires; since 2026-11-17 it asks the workers first, `TaskLauncher.is_active` (the workers only since 2026-11-27: no inline job left), Celery tasks are queued with `task_id=job_id`: a job that may still run gets 409 `confirmation_required` until `confirm=true`), and `job:{id}` at `running` until its 30-day TTL. No timeout on the jobs themselves, nor on the calls of the `etl/` scripts, **by decision** (2026-11-17: durations are never static, a forecast can exceed 10 min): never add one. Tests get the real gate on a temp db (`checkpoint_store` fixture) or `OpenGate`.
- The middleware logs full URLs, only `webhook_url` is masked (`api/middleware.py`, `_logged_url`): never put a secret in another query parameter, or mask it there. (`GET /api/config/` returns `has_dhis_token`, never the token.)
- **Mode per user and isolation (since 2026-11-19)**: the mode served is `core/job_context.current_test_mode()`: the session's (set by `get_current_user`, async, so the ContextVar reaches the route), or the job's (Celery kwargs `test_mode`, set by `_run_task`); test outside both. Every mode read of the store goes through its `test_mode` callable; every path through `work_dir` (`./input`, `./output` in production, `test/input`, `test/output` in test). What happens in one mode is never readable in the other: `cycles()`, `journal()`, the requests (`mode` of the session in the request's JSON; none: listed nowhere), job logs and their WebSocket (`has_job`). The three `fetch_*` scripts of `etl/` write `./input` whatever the mode: in test mode `etl_use_cases._into_mode_folder` sets production's file aside and moves theirs to `test/input` (safe because one job at a time). Tests: the autouse `production_mode` fixture and the async `app` user override serve production. See `docs/decision-design/mode-isolation/mode-isolation.md`.
- Tests: never `from tests.conftest import …` at module level or in a fixture of a new file: it re-runs conftest under a second name and replaces the `redis` mock, so `except redis.RedisError` stops matching in later tests (`test_auth.py`). Copy the small fake instead.
- Redis job state expires after 30 days. Older jobs only exist in `logs/`.
- Every route except `POST /auth/login`, `POST /auth/logout` and `GET /auth/dhis2-urls` requires the session (`main.py`, `_session`; `PUBLIC` in `test_route_protection.py`). No roles (removed 2026-11-17): every logged-in user may call every route, `DELETE /pipeline/lock` and the journal CSV included. Do not add an admin check without asking.
- A run's `forecast_report.html` is copied to `output/<cycle>/<pass>/report_<source>_<disease>.html` (`test/output/…` in test mode) when its `post_forecast` succeeds, because the next run empties `output/`. `GET /pipeline/runs/{source}/{disease}/report` serves it.
- Ports: `run_server.py` uses **8111**. `.vscode/launch.json` says 8000.

## Commands

Python 3.12 (use `test-venv`; the system `python3` is 3.11). Run from the repo root unless noted.

- Redis: `redis-server`
- Worker: `python -m etlhub.run_celery`
- Schema migrations (by hand, API and workers stopped): `python -m etlhub.migrate --check`, then `python -m etlhub.migrate`
- API: `cd etlhub && python -m run_server`
- Tests: `cd etlhub && ../test-venv/bin/python -m pytest tests -m "not integration"` (415 tests on 2026-11-27; bare `pytest` works too since `pytest.ini` is read)
- One file: `cd etlhub && ../test-venv/bin/python -m pytest tests/api/test_ingest_router.py`
- Linter / formatter: none configured. Do not invent one.

## Method for new code (proposed, see `etlhub/docs/DEVELOPMENT.md`)

- Work with the **ponytail** skill (root `CLAUDE.md`): reuse what `etlhub` already has (registries, `add_launch_route`, `CheckpointStore`) before writing anything new; mark deliberate shortcuts with `ponytail:`.
- Behaviour and its test ship in the same commit. For a new endpoint, task, service or bug fix, write the failing test first. 61 of 83 source commits came with their tests (audit 2026-11-27); whether the test came first does not show, so say what you did instead of claiming TDD.
- Assert behaviour, not only `status_code` (34 of 318 test functions only check it, audit 2026-11-27).
- New or changed functions: at most 50 lines and 4 parameters, annotated, no `except … pass`, no `print(`.
- Line coverage 93 % (audit 2026-11-27): do not lower it for the files you touch.

## Required checks

- `conftest.py` replaces Redis, `pridec_gee`, `pivot_dhis_tools`, `earthengine_api` and geopandas with global `MagicMock`s: a passing test says nothing about real Redis behaviour. `ee` (the real earthengine module) is not mocked.
- Patching `etlhub.core.config.get_settings` or `etlhub.core.dependencies.get_*` does not affect code that already imported the name. Use `app.dependency_overrides`. `get_checkpoint_store` and `get_request_tracker` are `lru_cache` singletons: tests fill them with `use_instance` (`tests/conftest.py`).
- Run the tests before and after any change in this module.
